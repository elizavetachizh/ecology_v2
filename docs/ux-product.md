# UX / Product — кабинет эколога

**Статус:** актуально на 2026-08-18  
**Аудитория:** эколог организации (не разработчик, не администратор Keycloak)  
**Архитектура и API:** [`frontend-architecture.md`](./frontend-architecture.md)

Этот документ заменяет устаревший wireframe полного продукта (операции 4 типов, лимиты, паспорта, ПОД-9/10/1-отходы как готовые разделы). Ниже — **как устроено сейчас**, **где это мешает**, и **какой UX целевой при текущем backend**.

---

## 1. Зачем продукт

Эколог должен:

1. завести нормативную базу организации (инструкция, структура, отходы, источники);
2. сказать системе, *где* какой отход учитывается (привязки);
3. каждый день фиксировать движение: образовалось / использовано;
4. видеть остаток и не уйти в минус;
5. позже — сдать ПОД-9 / ПОД-10 / 1-отходы.

Пока закрыты шаги 1–3 и частично 4 (остаток в мастере операции). Шаг 5 — не продукт.

Ключевой принцип:

> Система ведёт от контекста к действию и не показывает то, чем нельзя воспользоваться.

## 2. Ментальная модель (как объяснять в UI)

Три слоя, которые нельзя смешивать в одном слове «ПОД-9»:

| Слой | Сущность | Слова в UI |
|------|----------|------------|
| Документ | Инструкция (`mdm/instructions`) | «Инструкция по обращению с отходами» |
| Место учёта | Unit с `is_pod9` | «Место учёта отходов» (допустимо бейдж «ПОД-9») |
| Движение | Operation | «Образовано» / «Использовано» |
| Отчёт | будущего API | «Отчёт ПОД-9» — только когда появится формирование |

Сейчас в интерфейсе unit с флагом называется «журнал ПОД-9». Это понятно разработчикам, путает эколога: он думает, что создал отчёт, а создал место учёта.

Рекомендуемые подписи:

- кнопка: **«Добавить место учёта»**, не «Создать журнал ПОД-9»;
- бейдж в дереве: **ПОД-9**;
- описание: «На этом узле ведётся учёт отходов по инструкции».

## 3. Целевой каркас

### Левое меню (рекомендуемое)

**Работа**

- Главная
- Журнал операций
- Остатки *(когда появится экран на существующий `GET /operations/balances`)*

**Подготовка данных**

- Инструкции
- Структура организации
- Отходы
- Источники образования
- Все справочники (хаб)

**Низ сайдбара**

- Выход — **один** раз (сейчас дублируется с шапкой)

Убрать из меню до появления API: «Лимиты», «Нормативы», «ПОД-10», «1-отходы».  
«ПОД-9» в Отчётах — либо скрыть, либо явно пометить «черновик / не для учёта».

«Остатки отходов» сейчас ведёт на `/waste/balances` → 404. Это хуже, чем отсутствие пункта.

### Шапка

Оставить:

- активная организация (tenant);
- профиль;
- выход.

Убрать до появления смысла:

- колокольчик уведомлений (кнопка ничего не делает);
- leftover title `Acme Inc` у логотипа.

Не добавлять в шапку глобальный селект инструкции, пока операции **не** привязаны к инструкции на API. Иначе пользователь будет думать, что фильтр влияет на журнал, а он не влияет.

Быстрая кнопка **«+ Операция»** в шапке — да, это основной ежедневный сценарий. Сейчас она только на странице журнала.

## 4. Сценарии пользователя

### 4.1. Первый запуск (онбординг)

Порядок, который уже намекает хаб справочников — его нужно довести до конца:

```text
1. Выбрать организацию (если их несколько)
2. Создать инструкцию (можно черновик, затем даты и «действует»)
3. Построить дерево подразделений
4. На нужных узлах включить место учёта (is_pod9)
5. Завести отходы из классификатора
6. Завести источники образования
7. На месте учёта: выбрать инструкцию → привязать отходы + источники
8. Первая операция «Образовано»
```

Сейчас после логина — пустая «Главная»: «Каркас приложения: боковое меню и верхняя панель». Это нулевой value.

Целевая главная до KPI:

- если нет tenant — «Выберите организацию»;
- чеклист готовности (инструкция / структура / отход / привязка / операция) со ссылками;
- кнопка «Создать операцию», если справочники уже есть;
- никаких выдуманных цифр.

### 4.2. Ежедневный учёт

```text
Журнал → Создать операцию
  1. Место учёта (unit is_pod9)
  2. Отход (из привязанных к этому месту)
  3. Дата, тип, количество, источник (если образовано)
  4. Проверка: остаток до → изменение → остаток после
  → Провести
```

Сейчас мастер из 3 шагов, без шага проверки; unit и waste — любые из справочника; связь с инструкцией не участвует.

### 4.3. Два входа в привязку — это плюс

| Откуда | Зачем экологу |
|--------|----------------|
| Карточка места учёта | «Что учитываем на этой площадке» |
| Карточка отхода | «Где учитывается этот вид отхода» |

Оставить оба. Унифицировать слова: не «журнал ПОД-9» на одной стороне и «структурная единица» на другой.

## 5. Экраны as-is и UX-заметки

### 5.1. Главная `/`

Заглушка. Приоритет P0: заменить на чеклист + быстрые действия. Графики и KPI — после экрана остатков.

### 5.2. Хаб справочников `/directories`

Плюс: карточки, понятный CTA «Открыть», намёк «начните с инструкции».

Минусы:

- нет счётчиков записей;
- карточки «Лимиты» и «Нормативы» открывают заглушку — ложное ощущение полноты;
- описание инструкций: «по экологическому мониторингу» — неверный термин;
- описание структуры про «журналы ПОД-9 в одном дереве» — жаргон.

### 5.3. Инструкции

Список: поиск, фильтр статуса, пагинация, empty state — хорошо.

Форма: **ложный copy**. «После сохранения инструкция становится активной» — на API default `draft`, для `active` нужны даты. Эколог не поймёт, почему документ «не действует».

Целевой поток:

1. сохранить черновик (достаточно имени);
2. заполнить период;
3. явная кнопка «Ввести в действие» (не прятать статус в селекте без объяснения).

После создания — CTA «Перейти к структуре», не глухой возврат в таблицу.

### 5.4. Структура организации

Дерево + поиск + фильтр «только ПОД-9» — правильная модель. Создание дочернего узла из строки — хорошо.

Путаница:

- две сущности в одном дереве без легенды;
- «Создать журнал ПОД-9» vs «Добавить структурную единицу»;
- карточка обычного unit снизу снова предлагает «создать журнал» — дубль с кнопкой в шапке формы.

Целевой: легенда (узел / место учёта), одна точка создания места учёта, breadcrumb как сейчас оставить.

### 5.5. Отходы

Каталог через классификатор (`code + name`) — верно, не давать вводить код руками.

На карточке — зеркальные привязки WIU. Хорошо.

После create — сейчас hint «потом привяжете». Лучше: «Сохранить и привязать к месту учёта» (остаться на карточке).

### 5.6. Источники образования

Простой CRUD. Для ежедневной работы этого достаточно.

В мастере операции ссылка «создать в справочнике» **уводит с формы** и теряет черновик. Целевое: inline-создание источника (модалка поверх мастера) — API позволяет.

То же для отхода: ссылка на `/directories/wastes/new` разрывает сценарий.

### 5.7. Привязки UIW / WIU

Паттерн вкладок инструкции + таблица + модалка — правильный.

Улучшения:

- на unit без привязок вкладки инструкций пустые (`GET .../units/{id}/instructions` отдаёт только уже использованные). Неочевидно, как начать: нужен empty state «Выберите инструкцию и привяжите первый отход» с селектом **всех** инструкций, не только уже привязанных.
- `transport_unit` без пояснения. Tooltip: «транспортная единица — сколько отходов в одной транспортной таре; 0 если не используется».
- 409 duplicate — человеческая фраза: «Этот отход уже привязан к этой инструкции».

### 5.8. Журнал операций

Это ядро продукта. Таблица, фильтры, empty state, confirm delete с пересчётом остатков — хороший уровень.

Типы в UI: «Образовано» / «Использовано». Не подменять их четырьмя типами из старого wireframe (`вывоз`, `передано`, `поступило`) — **на API их нет**. Если продукт захочет «вывоз», это новый `operation_type` на backend.

Мастер:

| Сейчас | Нужно |
|--------|--------|
| 3 шага | 4-й: проверка остатка до/после |
| любой unit | по умолчанию только `is_pod9` (с переключателем «все») |
| любой waste | отходы, привязанные к выбранному unit (если product согласится; API не форсит) |
| остаток hint с шага 2 | оставить + показать дельту на шаге 4 |
| нет документа-основания / комментария | не рисовать поля без API |
| edit тем же мастером | ок |

Предупреждение при `used` > остатка — уже придёт 400 с backend. Показать **до submit**, сравнив amount с current balance.

### 5.9. Остатки

Пункта с рабочей страницей нет, API списка есть. Это главный пробел пользы: эколог ведёт журнал, но не видит картину на дату.

Минимальный экран:

- фильтры: дата / unit / waste (query API);
- таблица: отход, место, дата снимка, остаток, ЕИ;
- без графиков и «заполненности» — для них нужны лимиты.

Цвета заполненности из старого wireframe **не применять**, пока нет лимитов: зелёные полоски без лимита врут.

### 5.10. Отчёты

`/reports/pod-9` — тестовый preview с зашитыми `department: "321"`. В меню рядом мёртвые ПОД-10 и 1-отходы.

Для доверия: спрятать раздел «Отчёты» целиком до контракта. Показывать harness только за feature-flag / dev.

## 6. Визуальные правила (без смены стека)

Уже есть и стоит держать:

- светлая тема, белые карточки, левое меню;
- `PageContextBar` (заголовок + описание + CTA);
- `TenantRequiredGate`;
- `DataTable` + pagination + empty;
- toast после мутаций;
- `ConfirmDialog` на delete;
- badge статуса инструкции;
- combobox с поиском для длинных справочников.

Не делать:

- тёмную тему «для красоты»;
- декоративные графики на пустых данных;
- вторую кнопку выхода;
- пункты меню-призраки.

Микрокопи:

- ошибки API — человеческий язык, не сырой `detail` где можно;
- обязательные поля с `required` на label (как в операции);
- подсказки рядом со сложными полями, не в отдельной «справке».

## 8. Backlog удобства (по ценности для эколога)

### P0 — доверие и «можно пользоваться»

1. Убрать из меню 404 и заглушки (остатки-ссылка, ПОД-10, 1-отходы, лимиты, нормативы).
2. Главная = чеклист онбординга, не «каркас».
3. Copy инструкции: черновик vs «действует», обязательность дат.
4. Убрать пустой колокольчик и «Acme Inc».
5. Один logout.

### P1 — ежедневный сценарий

6. Экран остатков на `GET /operations/balances`.
7. Мастер операции: шаг «проверка» + блок «нельзя списать больше остатка».
8. `+ Операция` в шапке.
9. Селекты в мастере: места учёта и (желательно) только привязанные отходы.
10. Empty state UIW: выбрать инструкцию из полного списка, чтобы сделать первую привязку.
11. Переименовать «журнал ПОД-9» → «место учёта».

### P2 — не терять контекст

12. Inline-создание источника (и по возможности отхода) из мастера.
13. После create instruction/waste — CTA на следующий шаг цепочки.
14. Счётчики на карточках хаба (`total` из Page).
15. Иерархический select tenant, если дерево филиалов реальное.

### P3 — позже, нужен API

16. Отчёт ПОД-9 как мастер (параметры → проверка → файл).
17. Лимиты / заполненность / предупреждения.
18. Типы «вывоз / передано» и паспорта.
19. Dashboard KPI.
20. Глобальная инструкция в шапке — только если операции станут instruction-scoped.

## 9. Что сознательно не переносим из старого wireframe

| Было в wireframe | Почему не делаем сейчас |
|------------------|-------------------------|
| 4 типа операций + статусы «черновик / требует проверки» | API: `formed` / `used`, операция сразу проводится |
| Глобальная инструкция в шапке | операции без `instruction_id` |
| Создание отхода из узла «с нуля» (имя+код) | код живёт в классификаторе; MDM waste = ссылка |
| Progress bar мест хранения | нет лимитов |
| Журнал паспортов, контрагенты, договоры | нет API |
| ПОД-9/10/1-отходы как продуктовые разделы | нет archive/generate контракта |
| Тип узла структуры (цех / площадка / склад) | иерархия только `parent_id` + `is_pod9` |

Когда появится соответствующий backend doc — добавлять экран по тому же паттерну, что журнал операций, без угадывания модели.

## 10. Definition of Done для «удобно пользоваться»

Эколог без обучения разработчика может:

- [ ] понять, с чего начать, за 10 секунд на главной;
- [ ] не попасть в 404 из меню;
- [ ] завести инструкцию и понять, что она ещё черновик;
- [ ] отметить места учёта в дереве;
- [ ] привязать отход к месту и инструкции с любого из двух входов;
- [ ] провести «образовано» и увидеть, что остаток вырос;
- [ ] не провести «использовано» больше остатка — с понятным текстом;
- [ ] открыть список остатков по организации.

Пока не выполнены P0 и пункты 6–7 из P1, продукт выглядит как набор справочников, а не как учёт.
